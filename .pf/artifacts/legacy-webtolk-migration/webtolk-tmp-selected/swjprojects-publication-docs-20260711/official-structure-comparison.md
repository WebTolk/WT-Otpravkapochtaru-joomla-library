# Сверка с официальной структурой Otpravka API

Источник проверки: <https://otpravka.pochta.ru/specification#/main>.

Дата подготовки: 2026-07-11.

## Вывод

Текущая документация библиотеки соответствует официальной структуре по основному потоку отправки: авторизация, настройки, нормализация данных, тариф, заказы, партии, документы, возвраты, поиск ОПС и справочники. Для публикации в SW JProjects подготовлена более человеческая структура: она не повторяет полный каталог официальных методов, а показывает поддерживаемый рабочий путь Joomla-разработчика.

Пробелы не являются ошибкой документации, если они явно обозначены: библиотека не заявляет публичную поддержку архива, таймслотов, долгосрочного хранения, заявлений, пользовательских сессий и всех вариантов печатных форм.

## Официальные разделы и покрытие в проекте

### Главная страница, основные шаги, авторизация

В проекте покрыто через `README.md`, `docs/developer-api.md`, `docs/api/account-and-configuration.md` и настройки системного плагина.

Для публикации оставлен практический блок «Установка и настройка», без переноса служебных деталей официального кабинета.

### Данные

Официальный раздел включает нормализацию адреса, ФИО, телефона, расчёт тарифа и текущий остаток запросов. В библиотеке это покрыто методами фасада:

- `cleanAddress()`;
- `cleanPhysical()`;
- `cleanPhone()`;
- `getTariff()`;
- `getTariffAndDeliveryPeriod()`;
- `getApiLimit()`.

В публикационной документации этот блок поставлен перед созданием заказа, потому что практический сценарий должен начинаться с нормализации.

### Заказы

Официальный раздел заказов покрыт основными операциями:

- `createOrders()`;
- `editOrder()`;
- `findOrderById()`;
- `findOrderByShopId()`;
- `findOrderByRpo()`;
- `deleteOrders()`;
- `returnOrdersToNew()`;
- `getRecipientReliability()`;
- `getRecipientsReliability()`.

Для публикации выбран пример создания заказа после нормализации адреса, ФИО и телефона.

### Партии и документы

В проекте покрыты создание партии, просмотр партий и заказов в партии, генерация пакета документов и Ф103:

- `createBatch()`;
- `getAllBatches()`;
- `getOrdersInBatch()`;
- `generateDocumentPackage()`;
- `generateDocumentF103()`.

Официальная спецификация содержит больше печатных форм. В публикационной версии это ограничение указано явно.

### Возвраты

Раздел покрыт методами:

- `createReturnShipment()`;
- `createReturnShipments()`;
- `editReturnShipment()`;
- `deleteReturnShipment()`.

Публикационный текст объясняет два варианта: возврат по прямому отправлению и отдельное возвратное отправление.

### Поиск ОПС

Покрытие:

- `searchPostOfficeByIndex()`;
- `searchPostOfficeByAddress()`;
- `searchPostOfficeByCoordinates()`;
- `getPostOfficeServices()`;
- `getPostalCodesInLocality()`.

Отдельно отмечено, что локальный список стран не расходует лимит REST API.

### Настройки

Покрытие:

- `getAccountInfo()`;
- `getSettings()`;
- `getShippingPoints()`;
- `getApiLimit()`.

В публикационной документации этот блок встроен в настройку плагина и безопасность хранения ключей.

### Описание свойств

Официальный раздел содержит справочные значения и статусы. В проекте часть справочников покрывается локальными сущностями, константами payload и JSON Schema из `docs/api-schemas/otpravka/`.

Для сайта не стоит переносить большие справочные таблицы. Вместо этого публикационная версия ссылается на полную документацию и схемы.

### SOAP-отслеживание

Трекинг находится вне REST-структуры Otpravka API, но важен для пользователя пакета. В библиотеке он покрыт методами:

- `getOperationsByRpo()`;
- `getNpayInfo()`;
- `getTickets()`;
- `getOperationsByTicket()`.

В публикационной документации трекинг вынесен отдельным блоком и объясняет, что для SOAP нужны отдельные доступы.

## Непокрытые официальные разделы

В публичной документации явно названы разделы, которые не являются публичной поверхностью библиотеки:

- архив партий;
- долгосрочное хранение;
- временные интервалы и бронирование;
- заявления;
- пользовательские сессии;
- дополнительные печатные формы, кроме пакета документов и Ф103.

Если эти разделы понадобятся в будущем, лучше добавлять их отдельными эволюциями и живыми тестами API, а не описывать заранее.

## Рекомендации по публикации

- В SW JProjects вставлять HTML-фрагменты `publication-docs-ru.html` и `publication-docs-en.html`.
- Не вставлять большие таблицы методов в карточку проекта; для этого уже есть `docs/facade-method-reference.md`.
- Оставить карточку проекта неопубликованной до решения по версии/changelog и публичной загрузке пакета.
- После публикации проверить отображение блоков кода в редакторе сайта.
